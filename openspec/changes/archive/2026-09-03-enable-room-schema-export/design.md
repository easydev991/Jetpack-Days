## Context

См. proposal.md (Why). Техническая исходная точка:

- `DaysDatabase` (v2, Room 2.8.4), компилятор — KSP (`libs.plugins.ksp`), не kapt
- `MIGRATION_1_2` — единственная миграция: создаёт таблицу `reminders` + индекс `index_reminders_itemId`; таблица `items` между v1 и v2 не менялась
- Каталога `app/schemas/` нет, `room-testing` не подключён; MigrationTestHelper-тестов нет — существующий `DaysDatabaseMigrationTest` (app/src/test, JUnit 5 + MockK) — мок-юнит на структуру SQL-вызовов `MIGRATION_1_2` через `verify { database.execSQL(...) }` с `relaxed = true`; реального интеграционного теста миграции нет. **Мок-юнит удаляется** (tasks.md 3.3): он полностью перекрывается новым интеграционным `MigrationTest`, и оставлять его — мёртвый груз, создающий ложное впечатление покрытия
- androidTest-инфраструктура есть и работает (`make android-test`, примеры: `DaysDatabaseTest`, `ItemDaoTest` — Room in-memory, JUnit 4)

## Goals / Non-Goals

**Goals:**

- Экспорт схем Room в git, начиная с версии 2
- Верифицируемая миграция 1→2: MigrationTest, который создаёт БД v1 по схеме, прогоняет `MIGRATION_1_2` и валидирует результат против схемы v2 (включая сохранность данных пользователей)
- Конвенция, закрывающая долг в будущем: миграция без MigrationTest не принимается

**Non-Goals:**

- Переписывать `MIGRATION_1_2` на `@AutoMigration` задним числом — миграция уже в проде и работает, риск не оправдан (техническое обоснование — Risks)
- Отдельная CI-джоба: тесты миграции гоняются существующим `make android-test`
- Изменения формата бэкапа и чего-либо вне data/database-инфраструктуры

## Decisions

### 1. Схемы экспортируются в `app/schemas/` и коммитятся в git

KSP-аргумент `room.schemaLocation = $projectDir/schemas` + `exportSchema = true`.

- *Почему в git:* без истории схем MigrationTest и ревью миграций невозможны — это и есть закрываемый долг. Стандартная практика Room-проектов.
- *Альтернатива (не коммитить, хранить локально):* отвергнута — теряется весь смысл.
- *Новый json в diff при каждой миграции:* принимается как осознанный шум; это точка ревью — по нему видно, что именно изменилось в схеме.

### 2. Реконструкция `1.json` — правкой сгенерированного `2.json`

Порядок: сначала включается экспорт и генерируется честный `2.json`; затем `1.json` создаётся из него: удалить entity `reminders` (вместе с его index), поставить `"version": 1`, identityHash оставить как есть (см. Risks).

- *Почему не из git-истории:* восстановление кода v1 (entities + конвертеры) и сборка схемы оттуда — хрупкая многошаговая работа ради одного файла; правка `2.json` даёт идентичный результат, т.к. `items` между версиями не менялся (подтверждается `MIGRATION_1_2`: единственный DDL — создание `reminders`).
- *Проверка корректности реконструкции:* entity `items` в `1.json` должна быть побайтово равна `items` в `2.json`; отличаются только `version`, отсутствие `reminders` и, как следствие, список entities. Это условие включено в code review чеклист задачи.
- *Альтернатива (не реконструировать, тестировать только будущие миграции):* отвергнута — на устройствах с установленной v1 миграция 1→2 ещё выполнится, и именно этот путь остаётся непроверенным.

### 3. MigrationTest через `MigrationTestHelper` с конструктором от класса БД

`MigrationTestHelper(InstrumentationRegistry.getInstrumentation(), DaysDatabase::class.java)` — Room 2.8.4. Конструктор от `Class<out RoomDatabase>` **не использует** KSP-аргумент `room.schemaLocation` (тот управляет только экспортом из KSP в файловую систему); helper читает схемы из assets instrumentation-контекста по пути `<packageOfDatabaseClass>/<version>.json`. Проект использует только KSP-плагин (без Room Gradle Plugin, который бы делал это автоматически), поэтому требуется явная настройка `sourceSets.androidTest.assets.srcDir("$projectDir/schemas")` в `android { }` — см. tasks.md 3.2.

Сценарий теста (без кода, контракт):

1. `createDatabase(TEST_DB, 1)` — helper создаёт БД v1 по реконструированному `1.json`
2. Вставка тестовой строки в `items` **raw SQL** — DAO текущего кода знает только схему v2, на v1 данные вносятся напрямую (это же проверяет, что реконструированная схема пригодна для записи)
3. `runMigrationsAndValidate(TEST_DB, 2, true, MIGRATION_1_2)` — прогон миграции + структурная валидация против `2.json` (Room сверяет все таблицы, колонки, индексы, foreign keys)
4. Чтение вставленной строки — данные пережили миграцию
5. Дополнительно: запись в `reminders` после миграции — таблица и FK реально работоспособны

Файл: `app/src/androidTest/java/com/dayscounter/data/database/MigrationTest.kt`, JUnit 4, по конвенциям проекта (`kotlin-ui-testing` skill).

### 4. Конвенция на будущее (фиксируется в задачах, не кодом)

- Каждая новая миграция коммитится в паре с MigrationTest (схема N.json генерируется сборкой автоматически и попадает в тот же коммит)
- Простые изменения схемы (новая колонка/таблица/индекс без перестройки данных) — предпочтителен `@AutoMigration`, рукописный SQL — только для сложных случаев

## Risks / Trade-offs

- [Реконструированный `1.json` не совпадает с исторической схемой v1] → Структурное равенство `items` в 1.json и 2.json проверяется ревью (миграция items не трогала); raw-SQL вставка в тесте подтверждает пригодность схемы. Остаточный риск признан приемлемым: цена ошибки — ложный результат теста, не прод.
- [identityHash в `1.json` — не историческое значение v1] → Для MigrationTest это не важно: helper пишет hash из json в `room_master_table`, а после `runMigrationsAndValidate` валидируется структура, не hash. В рантайме hash исходной версии тоже не проверяется (RoomOpenHelper.onUpgrade: миграции → validateMigration против целевой схемы → updateIdentity перезаписывает hash; checkIdentity сверяет только с текущей сборкой). Ограничение documented: реконструированный `1.json` годится для тестов, но НЕ для `@AutoMigration(from = 1, to = 2)` — spec auto-migration генерируется компилятором из этих бандлов, доверять прод-миграцию реконструированному (не подлинному) артефакту нельзя.
- [Diff шум от схем в git] → Принимается; каждый json — факт изменения схемы, полезный для ревью.
