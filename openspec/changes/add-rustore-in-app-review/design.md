# Design

## Context

Кнопка «Оценить приложение» есть только в rustore flavor (гейт `BuildConfig.RUSTORE_FEATURES` в `MoreScreen`) и открывает `ACTION_VIEW` на браузерную ссылку из `AppConstants.APP_RATE_URL`. Flavor-дифференциация в проекте — только BuildConfig-флаги внутри `main`: flavor source-sets и flavor-зависимостей нет. DI — ручные фабрики (`AppModule`/`FormatterModule`) с выбором реализаций по флагам; хранилище настроек — `AppSettingsDataStore` (preferences DataStore, ключи в `PreferencesKeys`, suspend-сеттеры + Flow); аналитика — sealed interface `AnalyticsEvent` поверх `AnalyticsService` (Noop в debug); домен защищён guard-тестом `DomainPurityTest`. Сборка: minSdk 26, AGP 9 (flavor-aware имена задач; точная версия — `gradle/libs.versions.toml`), Kotlin 2.4.21. Автоматических запросов оценки в приложении нет. Мотивация — см. proposal.md; требования — см. specs/app-review/spec.md.

Ключевое ограничение SDK: публичного API предпроверки установки RuStore нет — установка проверяется внутри SDK, результат только через `onFailure` (`RuStoreNotInstalledException` из иерархии `RuStoreException`). SDK-флоу двухфазный: `requestReviewFlow()` → `ReviewInfo` (~5 минут жизни) → `launchReviewFlow(reviewInfo)`; лимит отображений регулируется на стороне RuStore.

## Goals / Non-Goals

**Goals:**

- Изолировать SDK целиком в flavor-артефактах: github-сборка компилируется и работает без SDK-зависимости.
- Сохранить чистоту домена: контракт лаунчера и milestone-логика — без android-типов, проходят `DomainPurityTest`.
- Переиспользовать проектные паттерны: ручной DI фабриками, preferences DataStore, sealed-события аналитики, TDD на доменную логику.

**Non-Goals:**

- Не менять функциональность github flavor (кнопка «Проверить обновления» и остальное — без изменений).
- Не менять кнопку «Оценить приложение» — отображение и поведение как сейчас (`ACTION_VIEW` на `AppConstants.APP_RATE_URL`); SDK-флоу кнопкой не инициируется (решение владельца; соответствует рекомендации доков SDK не использовать кнопку как триггер).
- Не подключать BOM RuStore и другие SDK RuStore (billing/push) — только review.
- Не строить собственные UI-диалоги оценки и не задавать пользователю вопросов до/во время SDK-флоу (прямо запрещено правилами SDK).
- Не отслеживать «пользователь уже оценил» своими механизмами — только через ошибки SDK.
- Не учитывать записи, созданные импортом бэкапа, в счётчике триггеров.
- Не повышать лимит Detekt и не вводить исключения из офлайн-правила в коде.

## Decisions

### D1. Первые flavor source-sets вместо расширения BuildConfig-паттерна

Код, импортирующий классы SDK, физически не может лежать в `main`: с зависимостью `rustoreImplementation` github-сборка сломается на компиляции. Поэтому вводятся `app/src/rustore/` и `app/src/github/` — первые flavor source-sets в проекте.

- В каждом source-set — своя реализация контракта лаунчера и своя фабрика с одинаковым публичным FQN: `main` ссылается на фабрику один раз, конкретная реализация подставляется на этапе компиляции flavor'а (стандартный flavor-паттерн), выбор не идёт через `if (RUSTORE_FEATURES)` в рантайме.
- Альтернативы: reflection-загрузка SDK-класса из main (отклонено — хрупко, ломает R8-предсказуемость); `compileOnly` + рантайм-проверки (отклонено — не убирает классы из github-APK без дополнительной настройки); отдельный Gradle-модуль (отклонено — избыточно для одной интеграции).

### D2. Домен: чистый контракт + чистая milestone-логика

- Интерфейс лаунчера review-флоу — в домене, без android-типов: методы запуска флоу и результат через `Result`/колбэк. Реализация в rustore source-set оборачивает `RuStoreReviewManagerFactory.create(context)` и двухфазный флоу, маппит `RuStoreException`-иерархию в доменное представление исхода.
- Milestone-логика (пороги `[1, 5, 15]`, «наивысший достигнутый непройденный», лимит сессии, отметка пройденности) — отдельный чистый use case: вход — текущее состояние счётчиков, выход — решение «запланировать для milestone N / не запрашивать». Пороги — константа use case. Тестируется на JVM без Android. Флаг «авто-запрос уже выполнялся в этой сессии» (требование лимита сессии из спеки) — in-memory состояние presentation-слоя, не персистится и в хранилище из D3 не входит. Держатель флага — не отдельный ViewModel, а общий holder (in-memory singleton) в presentation-слое, раздаваемый через `AppModule` по образцу существующих фабрик: пишет его `MainScreenViewModel` при запуске авто-флоу (7.2), читает `CreateEditScreenViewModel` при планировании milestone (7.1) — оба ViewModel получают один и тот же экземпляр. Непоказанный pending не перезаписывается: пока pending существует, достижение более высокого milestone даёт решение «не запрашивать», промежуточный milestone остаётся непройденным и подхватывается при следующем создании записи после показа текущего pending — порядок 1→5→15 сохраняется, ни один порог не «проглатывается» (решение владельца: pending не перезаписывается, пока не показан).
- Проверка установки RuStore приложением не выполняется ни в каком виде: отсутствие RuStore проявляется как ошибка SDK-флоу (`RuStoreNotInstalledException`), которая в авто-режиме обрабатывается тихо (см. спеку, «Тихая обработка ошибок авто-запроса»). Собственная предпроверка из исходного плана (PackageManager + `<queries>`) была нужна только для ветвления кнопки — кнопка теперь SDK не вызывает, и предпроверка не нужна (D4).
- Альтернатива: вся логика в UI-слое (как сейчас `rateApp`) — отклонено: нет тестируемости и нарушает сложившуюся структуру.

### D3. Отдельное хранилище счётчиков

Новый preferences DataStore (`data/preferences/`, по образцу `AppSettingsDataStore`): счётчик созданных записей (int), пройденные milestones (строковый набор — int-набор сериализуется строкой, по аналогии с существующей обработкой enum-ключей), pending-milestone.

- Альтернатива: расширить `AppSettingsDataStore` новыми ключами — отклонено: смешивает пользовательские настройки UI с служебными счётчиками и усложняет точечный сброс.
- Сброс вызывается из флоу полного удаления данных (`Screen.AppData`, действие «Удалить все данные») — в том же месте, где удаляются записи.

### D4. Без предпроверки установки RuStore и без собственного `<queries>`

Приложение не проверяет установку RuStore самостоятельно: кнопка «Оценить приложение» SDK не вызывает (поведение без изменений), а авто-флоу узнаёт об отсутствии RuStore через ошибку подготовки данных (`RuStoreNotInstalledException`) и обрабатывает её тихо (см. спеку, «Тихая обработка ошибок авто-запроса»). Собственная проверка через `PackageManager` из исходного плана отброшена вместе с ветвлением кнопки — она была нужна, чтобы кнопка могла выбрать «SDK или браузер» до запуска флоу; теперь этот выбор не делается вовсе.

`<queries>` в манифесте приложения не нужен: SDK 10.5.2 сам декларирует видимость пакета RuStore intent-based (`<queries><intent><action android:name="ru.vk.store.provider.review.RemoteReviewFlowProvider"/></intent></queries>`) в манифесте библиотеки, и декларация мержится в приложение автоматически (manifest merger; подтверждено распаковкой AAR `ru.rustore.sdk:review:10.5.2` из официального репозитория SDK). Явный `<package android:name="ru.vk.store"/>` из исходного плана понадобился бы только PackageManager-предпроверке, которой больше нет.

### D5. Точки интеграции в UI

- **Хук счётчика** — `CreateEditScreenViewModel.saveItem`, ветка создания (`itemId == null`). Точка хука — после успешных `persistItem` и `applyReminderChange`, непосредственно перед `completeSuccessfulSave`: эта функция вызывает `onSaved()` → `onBackClick` → навигацию назад, то есть определяет момент закрытия экрана создания; экран закрывается только когда и вставка в БД, и операция с напоминанием прошли успешно (частичный успех — вставка прошла, напоминание упало — оставляет экран открытым с ошибкой через ранний `return@launch`). Регистрация до `onSaved()` гарантирует установку pending до возврата на список записей. Успешным сохранением для счётчика считается только сохранение, завершившееся закрытием экрана. Хук гейтится флагом `isReviewEnabled: Boolean`, который ViewModel получает через инъекцию (фабрика ViewModel передаёт `BuildConfig.RUSTORE_FEATURES`): на github-сборке счётчик не ведётся вовсе — согласуется со строгой формулировкой спеки «авто-запросы MUST NOT инициироваться ни при каких условиях»; unit-тесты 7.1 остаются в общем `app/src/test/` и передают флаг явно (true/false), рантайм-гейт их не ломает (решение владельца — инъекция флага, закрыло пункт ревью о расхождении негейтённого хука со спекой). Отдельного доменного use case создания записи в проекте нет (сохранение идёт через репозиторий из ViewModel), и заводить его только ради счётчика — лишний слой; поэтому хук — в presentation-слое, логика решения — в домене (D2). Импорт бэкапа (`ImportBackupUseCase`) хук не проходит — счётчик не растёт (осознанно, см. Non-Goals).
- **Показ pending** — Events-экран: при наличии pending-milestone — задержка ~0.8 с, затем запуск SDK-флоу и отметка milestone пройденным. Гейт — `RUSTORE_FEATURES`.
- **Кнопка** — `MoreScreen`: без изменений, продолжает открывать `ACTION_VIEW` на `AppConstants.APP_RATE_URL`; SDK-флоу кнопкой не инициируется (D4).
- **Аналитика** — новый тип события в sealed interface `AnalyticsEvent` (review-флоу: только авто-запрос, исход: показ / ошибка с типом). В debug автоматически Noop — отдельной логики не нужно.
- **Строки** — не добавляются: SDK рисует свой UI, кнопка использует существующую ссылку без изменений.

### D6. Подключение зависимости

- Версия в `gradle/libs.versions.toml`, подключение `rustoreImplementation(project-координата)`: прямая версия `ru.rustore.sdk:review:10.5.2` без BOM — в проекте один SDK RuStore, BOM оправдан при появлении второго.
- Репозиторий `https://nexus-external.rustore.ru/repository/maven-rustore-exposed` — с content-filter по группе `ru.rustore.sdk`, чтобы сторонний репозиторий не стал источником для остальных артефактов.
- Альтернатива BOM: отклонена на текущем скоупе (см. выше).

### D7. Тестовая стратегия

- **Unit (домен, TDD — тесты до логики)**: milestone-решения — первый/пятый/пятнадцатый milestone, повтор в сессии, попытанный milestone, сброс; контракт лаунчера на fake-реализациях.
- **Unit (данные)**: персистентность и сброс хранилища счётчиков.
- **Unit (flavor rustore)**: тесты классов из `app/src/rustore/` (SDK-лаунчер на MockK) живут во flavor test source set `app/src/testRustore/`; прогон — `make test FLAVOR=rustore`. Правило одного flavor — и для flavor unit-тестов: дефолтный `make test` собирает github-вариант (`FLAVOR ?= github` → `testGithubDebugUnitTest`), flavor-тесты молча не выполняет.
- **SDK-ветка автотестами не покрывается** (эмулятор без RuStore) — ручная проверка на реальном устройстве с установленным RuStore; чек-лист ручной проверки — в tasks.
- **`make memory-check`** — задача трогает UI и ViewModel.

## Risks / Trade-offs

- [Лимит отображений на стороне RuStore: SDK-флоу может не показать форму даже при успешном вызове] → авто-режим тихо завершается; milestone помечается пройденным при запуске флоу (безопасно против повторных «пустых» вызовов). Кнопка SDK не вызывает, поэтому доковская рекомендация «не использовать кнопку как триггер» выполняется сама собой.
- [Новый сторонний maven-репозиторий — расширение supply chain] → content-filter по группе `ru.rustore.sdk`, официальный URL из документации SDK, версия зафиксирована в `libs.versions.toml`.
- [Неизвестные транзитивные зависимости SDK, конфликт версий или сетевой стек внутри SDK] → на этапе реализации проверить дерево зависимостей (`app:dependencies` для rustore-варианта); сетевой стек в приложении не появляется — взаимодействие идёт через приложение RuStore.
- [Первый flavor source-set меняет устоявшийся паттерн «всё в main»] → задокументировать в docs/deployment.md; гард: github-вариант собирается без SDK-зависимости (компиляция и есть проверка изоляции).
- [minSdk SDK явно не заявлен в документации] → проверить на этапе реализации (у проекта minSdk 26 — выше типовых требований RuStore SDK); зафиксировать в docs/deployment.md, если есть ограничение.
- [ProGuard/R8-правила для SDK в документации не упомянуты] → проверить release-сборку rustore flavor; добавить правила в `app/proguard-rules.pro` при необходимости.
- [Ошибочная классификация исходов в аналитике исказит конверсию] → исходы фиксируются по фактическим результатам фаз SDK (подготовка/показ), а не по предположениям.

## Migration Plan

Обычная фича-ветка, релиз — штатным процессом rustore flavor (docs/deployment.md, `make`-цели flavor-aware). Миграций схемы БД нет. Откат — revert ветки: SDK-зависимость и flavor source-sets самодостаточны, обратной миграции данных не требуется (новый DataStore не читается старыми версиями). Разрывов совместимости формата бэкапа нет — фича его не затрагивает.

## Open Questions

Нет — все решения зафиксированы владельцем: пороги `[1, 5, 15]`, кнопка «Оценить приложение» остаётся без изменений (SDK только в авто-триггерах), сброс счётчиков при полном удалении данных.
